# HOMEii Product Architecture

## Product boundary

HOMEii is a HAOS-first dashboard platform, not a Lovelace theme and not a collection of cards. It owns configuration, discovery, presentation, editing, permissions, upgrades and migrations while Home Assistant remains the source of truth for entities, Areas, users and service execution.

## Runtime topology

```text
HA user
  │
  ▼
React Panel ───────► Integration Bridge ───────► HA registries/services
  │                        │
  │                        └── versioned HA Store + admin authorization
  ▼
Widget Runtime
  │
  └───────────────► Supervisor App (Ingress)
                           └── assets, backups, migrations, release channel
```

## Monorepo boundaries

```text
apps/
  panel/             HA runtime dashboard
  studio/            admin-only visual editor
packages/
  contracts/         versioned wire/storage contracts
  design-system/     tokens, primitives, accessibility
  widget-sdk/        capability model and widget API
  area-engine/       Area discovery and recommendations
  ha-client/         typed WebSocket/service adapter
custom_components/
  homeii/             authorization, registries, HA Store
homeii/               HAOS Supervisor App
docs/adr/             immutable architecture decisions
tests/                security and cross-layer contract tests
```

No package may import from an app. Widgets may depend only on `contracts`, `design-system`, `widget-sdk` and `ha-client`.

## Configuration precedence

```text
factory defaults
  → project/global profile
  → role/user policy
  → device profile
  → session state
```

Only administrators can persist configuration. Device and session state cannot widen permissions granted by the project profile.

HOMEii permissions are a deny-first restriction layer over HA authorization. They can reduce what a user sees or controls but can never grant access HA itself denies. Policies address projects, dashboards, pages, Areas, widgets, domains and individual entities with separate `view`, `control`, `edit` and `admin` actions.

## Entity model

Widgets never bind to a hard-coded entity ID in component code. They receive a `WidgetBinding` resolved by the Area Engine:

- requested domain;
- required and optional capabilities;
- Area scope;
- explicit administrator override;
- fallback candidates and availability state.

Explicit overrides always win over automatic recommendations. Deleted or unavailable entities produce a diagnostic state rather than a broken widget.

Every discovered HA entity domain is retained. Rich adapters enhance known domains; an `entity.generic` widget safely represents unknown or newly introduced domains using their advertised capabilities.

## Widget lifecycle

1. A widget package exports a versioned manifest.
2. The registry validates supported domains and capabilities.
3. The resolver selects compatible entities inside the allowed Area.
4. The runtime renders the widget inside an error boundary.
5. Services run through the HA client and return consistent feedback.
6. Settings are edited through schema-driven forms generated by Studio.

## Responsive contract

Components use container queries and semantic size classes (`compact`, `regular`, `expanded`) rather than device names or fixed tablet widths. Every widget declares minimum dimensions, supported sizes and overflow behavior. Wide layouts must fit one viewport; phone layouts may scroll vertically but may not overflow horizontally.

## Upgrade policy

- Semantic product versions.
- Every persisted document has `schema_version` and `revision`.
- Migrations are forward-only, deterministic and tested with fixtures.
- The App creates a backup before a schema migration.
- Runtime supports the previous schema during one release window.
- Stable, beta and development channels are isolated.

## Lovelace migration pipeline

`YAML → safe AST → HOMEii IR → Area matching → widget adapters → preview → admin approval → persisted project`

Templates and unknown custom card settings are treated as inert data and never executed during import. Unsupported cards are preserved as `legacy.lovelace-card` with a warning. The preview reports mapping confidence, unmatched views, missing entities and external dependencies. Only an HA administrator can preview or approve a migration.

## Quality gates

- TypeScript strict mode and Python type checking.
- Contract tests across TypeScript and Python.
- Unit tests for resolvers and migrations.
- Playwright snapshots at phone, tablet, wall panel and desktop sizes.
- Accessibility: keyboard navigation, focus visibility, reduced motion and WCAG contrast.
- Performance budgets: initial JS, render time, memory and camera concurrency.
- Security tests proving non-admin users cannot persist changes.
